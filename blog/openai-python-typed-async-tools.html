OpenAI adds typed async tools to its Python SDK.

A small release with a useful lesson for agent builders: make the behavior of your tools explicit.

OPTIONAL ASYNC CONFIGURATION · TYPED REQUESTS & RESPONSES

OpenAI released version 3.49.0 of its Python SDK on 10 November 2026. The headline addition in the official release notes is typed async function tools, alongside a fix for microphone recordings encoded as PCM WAV. For developers building Python AI agents, the function-tool change is the more relevant part of this release. [1]

THE UPDATE AT A GLANCE

The SDK now includes a typed, optional async setting for function tools in agent sessions and persisted agents. The schema describes it as controlling whether the agent continues without waiting for the function result.

What changed

The implementation adds the setting to function-tool request dictionaries and exposes it on response models. The affected definitions are in the SDK’s beta agent APIs. In a Python response object, the attribute is named async_, while the serialized API field remains async. This gives the setting an explicit place in the SDK’s types. [2]

That distinction matters for existing integrations. The change notes direct callers reading the previously undeclared field through getattr(tool, 'async') or tool.model_extra['async'] to use tool.async_ instead. Teams using these paths should review their code when upgrading.

Why agent builders should care

An agent workflow often combines tasks with different dependencies. Some work can continue in the background; another step may need a tool’s result before making a decision. Explicit configuration makes that choice easier to represent in application code.

Consider a hypothetical enquiry workflow: a business might acknowledge a request while a separate tool gathers supporting information. A later recommendation would still need to wait for the relevant result. The engineering task is to define those dependencies clearly and test the handoff. An async setting alone does not establish that a workflow is correct or that it will run faster.

The SDK change is useful because it makes a piece of that intent visible to type-aware development tools. Developers can work with a declared field instead of relying on an extra response property. The release notes do not provide a performance benchmark, so any speed or throughput benefit needs to be measured in the actual application.

A migration detail worth checking

The implementation notes also describe serialization behavior. Using model_dump(by_alias=True, exclude_unset=True) preserves an explicitly supplied true or false while keeping an omitted value absent. A plain model_dump(by_alias=True) can include async: None when the value was omitted. [2]

That is a practical reason to inspect the payloads your integration sends and stores. An omitted setting and an explicitly serialized value can carry different meaning in an API contract. Review the request and response paths that your own application uses.

What this means for business automation

For a business owner, the useful question is how an agent coordinates the tools behind a process. A clear workflow should show what starts a task, what can proceed independently, what must wait, and where a person needs to review the result.

For developers considering this update, I would start with a focused check:

  • Review whether the application uses the affected agent-session or persisted-agent function tools.
  • Check code that reads the async setting from tool response objects.
  • Test explicitly enabled, disabled, and omitted settings when serializing models.
  • Exercise slow tool responses and steps that depend on the tool’s output.

A practical perspective

Small SDK improvements can make agent code easier to understand and maintain. This release gives developers clearer types for one tool-execution setting. The broader work remains designing the process, checking dependencies, and validating the outcome against real business needs.
